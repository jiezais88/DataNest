## 2. 关键发现与修复

### 🐞 Bug：`UserService.unbindSso` 解绑后 `sso_subject` 残留

**现象**（SA-12 暴露）：调用 unbindSso 后 `auth_source` 恢复为 `LOCAL`，但 `sso_subject` 仍保留原 subject 值。直接后果：
- 已绑定用户被解绑后，再次以同一 IdP 登录第一分支（subject 命中）仍会直接登录该账号 → AC-8「解绑后 SSO 登录不再命中该账号」不成立
- 旁证：handoff 验证记录中 carol_local「LOCAL + subject=mock-sub-carol-003」的异常状态正是该 bug 的遗留痕迹

**根因**：`userMapper.updateById(user)` 使用 MyBatis-Plus 默认 `FieldStrategy.NOT_NULL`，`setSsoSubject(null)` 被忽略、未生成 SET 子句。

**修复**（对照 `unlockUser`/`resetLoginState` 同款写法，改用 `LambdaUpdateWrapper` 显式 set null）：
```java
userMapper.update(null, new LambdaUpdateWrapper<User>()
    .eq(User::getId, userId)
    .set(User::getSsoSubject, null)
    .set(User::getAuthSource, "LOCAL")
    .set(User::getUpdatedBy, currentUserId())
    .set(User::getUpdatedAt, LocalDateTime.now()));
```

**回归验证**：SA-12 修复前 `expect(ssoSubject).toBe('')` 失败；修复后通过。

**影响面**：仅 system 服务；已重建 `datanest-app-system` 容器。

## 3. 部署/环境关键结论

### 3.1 OIDC 浏览器跳转：显式 `authorizationEndpoint` 必要

**现象**：容器内 `OidcClientService` 走 OIDC Discovery 拿到的 `authorization_endpoint=http://host.docker.internal:9040/authorize`，浏览器跨域跳转到该地址在测试环境卡死（chromium 无法解析 `host.docker.internal`）。

**根因**：`host.docker.internal` 在 Windows Docker Desktop 仅对容器内可解析（→ 宿主机 Docker 网关），**宿主机浏览器无该 DNS 记录**。`curl` 因宿主机 socket 优先解析成功属偶然；chromium 走系统网络栈未命中。

**解决方案**：在 `sso-config.yaml` 显式指定 `authorizationEndpoint=http://localhost:9040/authorize`（覆盖 Discovery 端点），token/jwks 端点留空走 Discovery（容器内访问 `host.docker.internal:9040` OK）。三个端点都显式才跳过 Discovery，所以仅授权端点显式、其他走 Discovery 是最优组合。

```yaml
oidc:
  enabled: true
  issuer: http://host.docker.internal:9040   # id_token iss 一致
  authorizationEndpoint: http://localhost:9040/authorize   # 浏览器可达
  clientId: datanest
  redirectUri: http://localhost:8080/api/system/auth/sso/oidc/callback
```

**验证**：SU-02 E2E 点击「企业 SSO 登录」→ 浏览器跳 `localhost:9040/authorize`（mock-idp）→ mock-idp 302 到 callback → 302 `/login#ssoToken=` → 前端 `useEffect` 清 hash + `navigate('/')`，全链路 879ms 通。

**生产环境推论**：若真实 IdP 授权端点是公网可访问 URL（如 `https://idp.example.com/authorize`），无需此配置。仅 Mock IdP + 容器化本地测试时需要显式覆盖。

### 3.2 Nacos 配置热生效有秒级延迟

PUT `/system/auth/sso/config` 后立即 GET 仍可能拿到旧值（PUT 走 Nacos publishConfig → system 监听器推送内存）。测试断言需 `expect.poll` 等待生效（建议 10s 超时）。E2E 不影响（用户操作有间隔）。
