## 1. 产品概述

**DataNest** 是一站式开源数据中台，核心理念是 **"开发治理一体化"**
——将数据治理能力内嵌到数据开发流程中，让质量、血缘、标准不再是"开发之后补的作业"，而是开发过程中的自然产物。

### 产品愿景

> 让每个数据团队都能用上"建数据 → 管数据 → 用数据"闭环统一的数据中台，无需拼凑多个开源组件，无需在开发完成后再补治理。

### 产品一句话

DataNest = 数据集成 + 数据开发调度 + 数据治理 + 数据资产目录 + 数据服务 + **数据存储引擎** + **实时计算引擎**
，七位一体，从存储到计算到治理，一套搞定。

## 2. 问题陈述

### 2.1 用户痛点

当下数据团队普遍面临三大断层：

**断层一：开发与治理"两张皮"**

数据工程师用 Airflow/DolphinScheduler 开发任务，治理团队用 Atlas/DataHub 管元数据。开发时不管血缘，上线后手工补；质量规则开发完才想到加，反复返工。
**治理永远在追赶开发的脚步**。

**断层二：组件拼凑成本高**

要搭一套完整的数据中台链路，至少需要：采集工具（DataX/Flink CDC）+ 调度（DolphinScheduler）+ 元数据（Atlas）+ 质量（Griffin/Great
Expectations）+ 数据目录（DataHub）+ 服务网关（Kong）。每个组件独立部署、独立运维、独立学习， **人力成本和时间成本是统一方案的
3-5 倍**。

**断层三：数据发现效率低**

分析师需要一张表，过程通常是：问工程师 → 工程师查文档（如果没有就查代码）→ 找到表名 → 不确定字段含义 → 再问 → 可能找错了 →
重新找。 **平均找一张可靠数据表的时间是 2-4 小时**。

### 2.2 目标用户群

| 角色           | 核心诉求                         | 当前痛点                                           |
|----------------|----------------------------------|----------------------------------------------------|
| **数据工程师** | 高效开发、自动治理、稳定调度     | 开发完还要手动补元数据、补血缘、配权限，重复劳动多 |
| **数据分析师** | 快速发现数据、看懂数据、放心使用 | 找表难、理解字段含义难、不确定数据质量             |
| **治理管理员** | 统一标准、质量可控、安全合规     | 治理规则推行难、质量监控靠人肉、血缘链路不完整     |

### 2.3 不解决的代价

- 数据团队 **30-40% 的时间在重复造轮子**（搭环境、拼组件、手动写元数据）
- 数据质量问题发现滞后， **线上事故中 60%+ 与数据质量相关**
- 新人入职需要 **2-4 周**才能摸清数据资产全貌

## 3. 目标与非目标

### 3.1 MVP 目标

| #  | 目标                                                                       | 衡量标准                                                           |
|----|----------------------------------------------------------------------------|--------------------------------------------------------------------|
| G1 | 提供统一的数据中台体验，覆盖存储→集成→开发→治理→资产→服务→实时计算七大环节 | 用户可在单平台上完成完整数据链路，无需外接存储引擎                 |
| G2 | 实现开发治理一体化——开发任务自动生成血缘、自动关联元数据                   | 数据工程师无需额外操作即可产出完整的元数据和血缘                   |
| G3 | 提供自建 OLAP 分析引擎和湖仓引擎，实现高性能查询和数据湖 ACID 能力         | 查询性能不低于同配置 ClickHouse 的 70%；支持时间旅行和 Schema 演进 |
| G4 | 提供全链路自建实时计算能力——实时采集入湖、流处理计算、实时数据服务         | 端到端延迟控制在秒级；支持 Exactly-Once 语义                       |
| G5 | 提供可搜索、可理解的数据资产目录                                           | 分析师从"想问人"到"自己搜"，平均找表时间降至 5 分钟内              |
| G6 | 社区友好：清晰文档 + 快速启动脚本，新用户 30 分钟内完成部署                | 提供 Docker Compose 一键启动                                       |

### 3.2 非目标（Non-goals）

| #   | 非目标                           | 原因                                                                               |
|-----|----------------------------------|------------------------------------------------------------------------------------|
| NG1 | **不做 BI 可视化/仪表盘**        | 独立赛道，社区已有 Superset/Metabase 等成熟方案，DataNest 做集成不做自研           |
| NG2 | **不做 ML 模型训练平台**         | 属于 AI 中台范畴，与 DataNest 分开建设                                             |
| NG3 | **不做多租户 SaaS 化**           | 开源项目定位，多租户隔离属于企业版/商业版考虑范畴                                  |
| NG4 | **不做数据安全产品（DLP/加密）** | 仅做基础的 RBAC 权限和脱敏规则配置，不涉及底层加密存储、审计日志分析等安全产品能力 |

### 3.3 未来版本考虑（V2+）

- **AI 辅助能力**：智能 SQL 补全、自动质量规则推荐、异常检测
- **实时数据链路**：流批一体的任务编排和血缘追踪
- **DataOps 流水线**：数据 CI/CD、环境管理、自动化测试
- **企业版特性**：多租户、SSO 集成、审计合规加强

## 4. 用户角色与故事

### 4.1 角色定义

#### P1 — 数据工程师（Data Engineer）

- **技能水平**：熟悉 SQL/Python、ETL 流程、调度系统
- **工作内容**：搭建数据管道、开发 ETL 任务、管理任务依赖和调度
- **使用频率**：每日
- **核心场景**：创建数据源连接 → 开发 ETL 作业 → 配置调度 → 监控运行 → 排查故障

#### P2 — 数据分析师（Data Analyst）

- **技能水平**：熟练 SQL、了解基本数据模型，不关心底层技术实现
- **工作内容**：探索数据、写分析查询、做报表
- **使用频率**：每日
- **核心场景**：搜索数据表 → 理解表结构和含义 → 验证数据质量 → 获取数据查询入口

#### P3 — 治理管理员（Governance Admin）

- **技能水平**：理解数据治理体系，熟悉数据标准和合规要求
- **工作内容**：制定数据标准、配置质量规则、管理元数据和血缘、审计数据使用
- **使用频率**：每周 2-3 次
- **核心场景**：定义数据标准 → 配置质量监控 → 查看血缘关系 → 处理质量告警

### 5.1 模块依赖关系（v2.0 更新）

- **数据存储引擎** 是新的底层基础设施，为数据集成提供目标存储，为数据开发提供数据源，为数据服务提供查询加速
- **实时计算引擎** 与数据集成、数据服务深度关联——实时采集入湖仓、流处理计算、实时 API 推送
- **数据集成** 是上游基础，所有模块依赖数据源连接；离线批量写入存储引擎，实时流数据写入消息队列
- **数据开发** 依赖集成模块的数据源和存储引擎，为治理模块自动产生血缘和元数据
- **数据治理** 横跨所有模块：集成时做标准校验、开发时生成血缘、存储时管理生命周期、服务时做权限管控
- **数据资产目录** 消费治理模块产出，呈现给分析师
- **数据服务** 消费存储引擎（OLAP 查询）和实时计算引擎（实时推送），对外提供数据服务

### 5.2 模块优先级

| 模块           | MVP 优先级 | 理由                                                |
|----------------|------------|-----------------------------------------------------|
| 数据集成       | P0 — 必须  | 没有数据接入，其他模块无米下锅                      |
| 数据存储引擎   | P0 — 必须  | 数据中台的基础底座，OLAP + 湖仓是数据资产的物理载体 |
| 数据开发与调度 | P0 — 必须  | 核心工作流，用户最主要的使用场景                    |
| 数据治理       | P0 — 必须  | "开发治理一体化"的核心价值承载                      |
| 数据资产目录   | P0 — 必须  | 数据分析师的核心入口                                |
| 实时计算引擎   | P1 — 应该  | 离线链路先行，实时计算在核心模块稳定后启动          |
| 数据服务       | P1 — 应该  | 核心模块稳定后再深入                                |
| RBAC 权限      | P1 — 应该  | 单机模式下可简化                                    |

## 6. 模块一：数据集成

### 6.1 模块目标

提供统一的数据源连接管理，支持多种数据源的批量和实时数据采集，让数据工程师在一个界面上完成所有数据接入工作。

### 6.2 功能需求

#### P0 — 必须（MVP 不可或缺）

| ID    | 功能           | 描述                                                                              | 验收标准                                                            |
|-------|----------------|-----------------------------------------------------------------------------------|---------------------------------------------------------------------|
| DI-01 | 数据源连接管理 | 支持添加、测试、编辑、删除数据源连接，连接信息加密存储                            | 支持至少 5 种主流数据源类型；连接测试功能可用；连接信息不以明文存储 |
| DI-02 | 数据源类型支持 | 支持关系型数据库（MySQL、PostgreSQL）、大数据存储（Hive、HDFS）、云存储（S3/OSS） | 每种类型可通过标准 JDBC/驱动连接                                    |
| DI-03 | 批量数据同步   | 支持以任务形式配置批量数据同步（全量/增量），可视化配置源→目标映射                | 提供向导式配置流程；支持字段映射和简单转换                          |
| DI-04 | CDC 实时采集   | 支持基于数据库日志的实时变更数据捕获                                              | 支持至少 MySQL CDC；延迟在秒级                                      |
| DI-05 | 连接池与安全   | 所有数据源连接使用连接池管理，支持 TLS 加密传输                                   | 连接可复用；敏感信息脱敏展示                                        |

#### P1 — 应该（快速跟进）

| ID    | 功能             | 描述                                              |
|-------|------------------|---------------------------------------------------|
| DI-06 | 更多数据源       | Oracle、SQL Server、MongoDB、Kafka、Elasticsearch |
| DI-07 | 采集监控面板     | 实时展示各采集任务的吞吐量、延迟、错误数          |
| DI-08 | 数据预览         | 连接数据源后可预览前 N 条数据，确认配置正确       |
| DI-09 | 自动 Schema 推断 | 自动读取源表结构并生成目标表 DDL                  |

#### P2 — 未来考虑

| ID    | 功能           | 描述                                 |
|-------|----------------|--------------------------------------|
| DI-10 | API 数据源接入 | 支持 RESTful API、GraphQL 作为数据源 |
| DI-11 | 采集断点续传   | 大批量同步失败后可从断点继续         |
| DI-12 | 数据脱敏采集   | 采集过程中根据规则自动脱敏敏感字段   |

### 6.3 用户故事（集成模块）

| ID    | 用户故事                                                             | 对应功能     |
|-------|----------------------------------------------------------------------|--------------|
| DE-01 | 作为数据工程师，我希望在一个平台上完成数据源连接配置…                | DI-01, DI-02 |
| DE-10 | 作为数据工程师，我希望创建批量同步任务，将 MySQL 数据同步到数据仓库… | DI-03        |
| DE-11 | 作为数据工程师，我希望实时捕获业务数据库的变更并同步到下游…          | DI-04        |

## 7. 模块二：数据开发与调度

### 7.1 模块目标

提供可视化 DAG 编排的数据开发环境，支持 SQL 和 Python 任务，内置调度引擎，让数据工程师高效开发、编排和运维数据流水线。

### 7.2 功能需求

#### P0 — 必须（MVP 不可或缺）

| ID    | 功能            | 描述                                                                           | 验收标准                                                     |
|-------|-----------------|--------------------------------------------------------------------------------|--------------------------------------------------------------|
| DD-01 | DAG 可视化编排  | 拖拽式创建任务节点，连线定义依赖关系，形成有向无环图                           | 支持节点的增删改连；支持画布缩放和平移；自动检测循环依赖     |
| DD-02 | SQL 任务开发    | 在线 SQL 编辑器，支持语法高亮、格式化、多语句执行，关联数据源执行              | 支持 MySQL、PostgreSQL、Hive 的 SQL 方言；执行结果显示和导出 |
| DD-03 | Python 任务开发 | 在线 Python 脚本编辑器，支持基础库，可引用平台提供的上下文（数据源连接信息等） | 支持 Python 3.x；执行日志实时展示                            |
| DD-04 | 调度引擎        | 支持 Cron 表达式定时调度、手动触发、依赖触发（上游完成自动触发下游）           | Cron 精度到分钟级；支持时区配置；支持任务超时设置            |
| DD-05 | 任务运行监控    | 查看任务运行历史、实时日志、运行状态（等待中/运行中/成功/失败/超时）           | 日志实时流式展示；历史记录可搜索和筛选                       |
| DD-06 | 失败告警        | 任务失败时通过配置的通知渠道发送告警                                           | 至少支持邮件告警；告警内容包含任务名、失败时间、错误摘要     |
| DD-07 | 任务依赖管理    | 支持上下游任务依赖，支持跨 DAG 依赖                                            | 依赖关系可视化；上游失败时下游自动阻塞                       |

#### P1 — 应该（快速跟进）

| ID    | 功能         | 描述                                                         |

## 17. 竞品参考

### 17.1 主要竞品定位（v2.0 扩展）

v2.0 加入存储引擎和实时计算后，DataNest 的竞品对标升级：

| 竞品                 | 类型       | 覆盖范围                 | 与 DataNest 差异                                                  |
|----------------------|------------|--------------------------|-------------------------------------------------------------------|
| **Databricks**       | 商业/开源  | 湖仓 + 调度 + 治理 + ML  | 最接近 DataNest v2.0 的对标产品；但不开源，云绑定，治理能力相对轻 |
| **StarRocks**        | 开源 OLAP  | 极速 OLAP 查询，MPP 架构 | 仅覆盖 OLAP，无湖仓 ACID、无调度、无治理                          |
| **Apache Doris**     | 开源 OLAP  | OLAP 分析引擎            | 仅覆盖 OLAP，无湖仓、无开发调度                                   |
| **Apache Flink**     | 开源流处理 | 实时流处理引擎           | 仅覆盖流计算，非一站式平台，部署和运维门槛高                      |
| **RisingWave**       | 开源流处理 | 流处理数据库             | 仅覆盖流处理，无离线计算和治理                                    |
| **DolphinScheduler** | 开源调度   | 任务调度                 | 仅覆盖调度，缺少存储/治理/资产目录能力                            |
| **阿里 DataWorks**   | 商业       | 集成+开发+治理+服务      | 云绑定不开源，无自建存储引擎（依赖 MaxCompute）                   |
| **华为 DataArts**    | 商业       | 治理+集成+开发           | 云绑定不开源，侧重政企治理合规                                    |

### 17.2 DataNest v2.0 的差异化空间

现有方案的核心痛点分为两类：

**品类一：拼凑式方案（DolphinScheduler + Doris + Flink + Atlas + DataHub）**

- 用户需要拼装 5-7 个独立组件才能覆盖完整链路
- 组件间数据不通，血缘和质量信息无法自动流转
- 每个组件有独立的 UI、API、部署方式，学习成本极高

**品类二：商业平台（Databricks / DataWorks / DataArts）**

- 功能完整但云绑定，用户数据和技术栈被锁定
- 不开源，无法私有化定制和二次开发
- 定价昂贵，中小团队难以承受

**DataNest 的差异化在于**——在开源领域，它是唯一同时覆盖 OLAP 存储 + 湖仓 + 实时计算 + 开发调度 + 治理 + 数据服务的
**七合一开箱即用平台**。
